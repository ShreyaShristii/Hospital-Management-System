0 · Executive Summary

HMS started as a feature-rich but fragile MERN application: 15 modules and 7 roles, but no tests, no validation, a privilege-escalation bug at sign-up, and two competing visual styles. Three passes were made on it: engineering hardening, UX and design, and this documentation pass.

1 · Project Overview

What the application does

A role-based hospital platform. Seven roles (admin, doctor, patient, receptionist, nurse, lab staff, pharmacist) each see a tailored dashboard and navigation. Modules: appointments, patients, doctors, staff, departments, beds and admissions, electronic medical records (EMR), lab tests, pharmacy stock, billing with Razorpay online payment, reviews and notifications.

Original architecture

New architecture

Request lifecycle (end to end)

Key engineering decisions

  • Split app.js from server.js. Tests can import the app without opening a port or connecting to a database.
  • Validate at the edge, enforce in the database. Request validators reject bad input early; schema rules and unique indexes are the last line of defence (for example, preventing double-booking).
  • Never trust client-supplied identity or money. Role, doctor identity, bill totals and the bill being paid are all derived on the server.
  • Re-check the user on every request. One extra indexed lookup makes deactivation and role changes take effect immediately.
  • Incremental UI system, not a rewrite. Design tokens and shared layout first; existing screens keep working while they migrate.

Architecture

App / server split with a real bootstrap

backend/app.js · backend/server.js · backend/config/env.js · backend/config/db.js
Before
One server.js built the app, called connectDB() without awaiting it, and started listening immediately.
Now
app.js exports the Express app. server.js validates env, awaits the DB, listens, and shuts down gracefully on SIGTERM/SIGINT.
Why
The server could accept traffic before the DB was ready, and the app could not be tested without a live server.
Benefits
Testability, safe startup, clean container stops.
Recruiter impact
Shows you understand application lifecycle, not just routes.
Talking point
"I separated composition from runtime so Supertest can import the app, and the process only accepts traffic once dependencies are healthy."

Central route registry

backend/routes/index.js
Before
15 require and app.use pairs in server.js, inconsistently indented, including a commented-out duplicate.
Now
One map of path to router. ObjectId validation is attached to every router's :id-style params automatically.
Why
A cross-cutting rule (valid ids) should be applied once, not remembered per file.
Talking point
"Cross-cutting concerns go in one place so new routes get them for free."

Token service (first service-layer module)

backend/services/tokenService.js · authController.js · authMiddleware.js
Before
jwt.sign in the controller, jwt.verify in middleware, with no shared options.
Now
signToken / verifyToken with the algorithm pinned to HS256 and a configurable expiry.
Why
Security settings that live in two places drift apart.
Talking point
"JWT policy lives in one module; changing expiry or algorithm is a one-line change."
Backend

Centralized error handling and a standard error shape

middlewares/errorMiddleware.js · utils/AppError.js · utils/asyncHandler.js · all 15 controllers
Before
Every handler ended with res.status(500).json({ message: error.message }). The global handler existed but was unreachable. Bad ids returned 500.
Now
Controllers call next(error) or throw AppError. One handler maps CastError→400, ValidationError→400, duplicate key→409, JWT errors→401, and hides 500 messages in production.
Why
Leaking database messages helps attackers; wrong status codes break clients.
Benefits
Consistent { success:false, message, details? }; less code per handler.
Recruiter impact
One of the first things reviewers check in an Express codebase.
Talking point
"Controllers describe the happy path; one middleware decides status codes and what is safe to expose."

Health endpoint

routes/index.js · backend/Dockerfile (HEALTHCHECK)
Before
GET / returned a static string, even when the database was down.
Now
GET /api/health returns uptime and DB state; 503 when Mongo is disconnected. It is excluded from rate limiting.
Talking point
"Health reflects dependencies, so orchestrators restart or route away from a broken instance."

Structured logging

utils/logger.js · app.js · server.js
Before
console.log gated on NODE_ENV !== 'production', so production had no logs at all.
Now
pino JSON logs with a request id per request (honours x-request-id), and redaction of passwords and auth headers.
Talking point
"Every log line has a request id, so I can follow one user's failing request across the system."

Search that actually works

patientController.js · appointmentController.js · billController.js
Before
$regex on 'userId.name', a field that does not exist on the stored document, so it never matched. Appointments filtered in memory after pagination, so totals were wrong.
Now
Matching users are resolved first, then the query filters by their ids before skip/limit.
Talking point
"MongoDB populate is a client-side join, so you cannot query a populated field. I resolve references first."
Database

Schema validation, timestamps and indexes

models/User.js · Patient.js · Appointment.js · Bill.js
Before
No indexes; no timestamps, yet code sorted by createdAt; mixed-case emails; password hash returned by default.
Now
Length, format and range rules; lowercase emails; password select:false; timestamps; indexes on common filters; unique Patient.userId.
Talking point
"Validation at the API is for good error messages; validation in the schema is for data integrity."

Double-booking prevention (race-free)

models/Appointment.js
Before
Two patients could book the same doctor at the same time.
Now
A partial unique index on (doctorId, date, time) where status = 'Scheduled'. Collisions return 409.
Why
A "check then insert" in code has a race window; the database constraint does not.
Talking point
"I pushed the invariant into the database, so concurrent requests cannot violate it."
Security

Privilege escalation at registration

authController.js · authRoutes.js · client AddStaffForm.jsx
Before
role: role || 'patient', so {"role":"admin"} created an admin.
Now
Public sign-up always creates a patient. Staff accounts use the admin-only POST /api/auth/staff-accounts.
Recruiter impact
Removes the single biggest red flag in the repository.
Talking point
"Authorization data never comes from the client. Roles are assigned by a privileged path."

Login and session hardening

authController.js · authMiddleware.js · tokenService.js · models/User.js
Before
404 "User not found" vs 400 "Invalid password" (user enumeration); isActive ignored; bcrypt cost 10; JWT role trusted for 24h.
Now
One generic 401; comparison against a dummy hash flattens timing; bcrypt 12; inactive users rejected; every request re-reads role and active state.
Talking point
"Login doesn't reveal which emails exist, and deactivating a user takes effect on their next request."

IDOR and mass assignment

patientController.js · appointmentController.js · billController.js · labController.js · emrController.js · emrRoutes.js
Before
Any patient could list all patients or read anyone's lab results. findByIdAndUpdate(id, req.body) let callers overwrite any field. A doctor could author an EMR as another doctor.
Now
Ownership checks for patient-role reads; explicit allowlists for updates; EMR doctor derived from the token; route roles aligned with controller rules.
Talking point
"Role checks answer 'can you use this endpoint'; ownership checks answer 'can you touch this record'. You need both."

Payment integrity

paymentController.js · paymentRoutes.js · models/Bill.js
Before
billId came from the client at verification, so one valid signature could mark a different bill paid. String !== comparison. Mode 'Online' not in the schema enum.
Now
Order id stored on the bill at creation; verification looks the bill up by order id; timingSafeEqual; ownership check; idempotent; Razorpay public key returned to the client (fixes checkout not opening).
Talking point
"The server is the source of truth for which bill and how much. The client only relays Razorpay's signed proof."

Input validation and other hardening

validators/authValidators.js · middlewares/validate.js · utils/escapeRegex.js · app.js
Before
express-validator installed but unused; raw user input inside $regex; 10 MB body limit; plain-text rate-limit responses.
Now
Rules on auth and payment routes with field-level error details; ObjectId param checks; escaped and length-capped regex input; 100 KB limit; JSON 429 responses.
Talking point
"Unescaped regex is a ReDoS and query-injection vector; I escape and cap it."
Frontend

Global 401 handling and token attachment

client/src/utils/setupAxios.js · main.jsx · authSlice.js
Before
14 copies of getToken(); an expired token left the user on broken pages.
Now
One interceptor attaches the token and logs out on 401 (except on the login call itself). Validation details surface in auth errors.
Talking point
"Auth policy is a cross-cutting client concern, so it lives in an interceptor, not in every API call."

ErrorBoundary and real linting

components/common/ErrorBoundary.jsx · .eslintrc.cjs · constants/theme.js
Before
Any render error blanked the whole app; lint reported 247 errors, so nobody ran it.
Now
A fallback screen with reload; 0 lint errors (18 warnings), plus a real bug fixed (a duplicate object key).
Talking point
"A linter that always fails is ignored. I made it pass, so CI can enforce it."
UX & Design

Design tokens and one visual language

client/src/index.css · index.html · App.css (deleted) · 5 files with font @imports removed
Before
Login and dashboards used DM Sans with one navy; other pages used Arial with another. Fonts imported separately per component.
Now
CSS variables for color, spacing, radius and shadow; shared .btn, .surface, .page classes; fonts loaded once with preconnect.
Talking point
"Tokens first, components second: change the palette in one file and every screen follows."

Navigation rewrite

components/Navbar.jsx · Navbar.css
Before

Now

"Navigation is the most-used UI in the app, so I fixed discoverability and mobile first."

Shared page layout, states and feedback

PageLayout.jsx · TableSkeleton.jsx · EmptyState.jsx · Toast.jsx · StatusPage.jsx · NotFoundPage.jsx · 7 pages · PatientList.jsx · PaymentModal.jsx
Before
Each page re-implemented its header inline; "⟳ Loading..." text; bare-text empty states; a plain <h1> 403 page; blank screen for unknown URLs; alert() for payment results.
Now

"Every async screen has four states (loading, empty, error, success), and I designed all four."

4 · Interview Cheat Sheet

What is centralized error handling?

Short answer: One middleware turns every thrown or forwarded error into an HTTP response, so status codes and error shape are decided in one place.

How we used it: Controllers call next(err) or throw AppError; errorMiddleware.js maps Mongoose/JWT errors and hides 5xx details in production.

Why industry uses it: Consistent APIs, no leaked stack traces, a single place to log and alert.

Follow-ups: Why does Express need 4 arguments for error middleware? · How do async errors reach it in Express 4 vs 5? · Operational vs programmer errors?
Authentication vs authorization? What is IDOR?

Short answer: Authentication proves who you are; authorization decides what you may do. IDOR is when changing an id in the URL gives access to someone else's record.

How we used it: protect (authn) → authorize(roles) (route-level authz) → ownership checks in controllers (object-level authz).

Why industry uses it: Broken access control is #1 in the OWASP Top 10.

Follow-ups: RBAC vs ABAC? · Where would you centralize ownership policies? · How do you test an authz matrix?
How does JWT authentication work, and what are its weaknesses?

Short answer: The server signs a token containing claims; clients send it on each request; the server verifies the signature without a session store.

How we used it: HS256 pinned, 1-day expiry, and a per-request user lookup so revocation works.

Why industry uses it: Stateless scaling across services. Weaknesses: hard to revoke, and XSS can steal tokens from localStorage.

Follow-ups: Refresh tokens? · httpOnly cookies vs localStorage? · What is the alg: none attack?
Why validate input, and where?

Short answer: Never trust the client. Validate at the API edge for good errors, and in the schema/database for integrity.

How we used it: express-validator chains + a validate middleware; ObjectId param checks; Mongoose schema rules; field allowlists against mass assignment.

Follow-ups: express-validator vs Zod vs Joi? · Validation vs sanitization? · What is mass assignment?
What is rate limiting?

Short answer: Capping requests per client per time window to stop brute force and abuse.

How we used it: A global limiter, plus a strict one on login and register that skips successful requests; health checks excluded.

Follow-ups: Why does an in-memory limiter break with multiple instances? (Use Redis.) · Token bucket vs fixed window? · Per-IP vs per-account?
What makes logging production-grade?

Short answer: Structured (JSON), leveled, correlated by request id, and free of secrets.

How we used it: pino + pino-http, a request id per request, redaction of auth headers and passwords.

Follow-ups: Logs vs metrics vs traces? · What would you alert on? · How would you ship logs to ELK / Datadog?
Liveness vs readiness: what is a health check?

Short answer: An endpoint orchestrators poll to decide whether to restart an instance or send it traffic.

How we used it: /api/health returns 503 when Mongo is down; Docker HEALTHCHECK uses it.

Follow-ups: Should liveness depend on the DB? · How does Kubernetes use each probe?
Unit vs integration tests? What did you mock?

Short answer: Unit tests check one function in isolation; integration tests check pieces working together, here the full HTTP stack.

How we used it: Supertest drives real routes and middleware; Mongoose models are mocked with Jest. Next step: mongodb-memory-server for real queries.

Follow-ups: The test pyramid? · Risks of over-mocking? · How do you test race conditions?
What is CI/CD?

Short answer: CI verifies every change automatically; CD ships verified changes automatically.

How we used it: GitHub Actions runs backend tests, client lint/test/build, then Docker builds, on every push and PR.

Follow-ups: Caching dependencies? · Branch protection? · Where do secrets live? · Blue/green vs canary?
Why Docker? What is a multi-stage build?

Short answer: Containers package the app with its runtime so it behaves the same everywhere. Multi-stage builds keep build tools out of the final image.

How we used it: API image with production deps only, running as a non-root user; client built then served by nginx; Compose for the full stack.

Follow-ups: Image vs container? · Why non-root? · Layer caching order? · Compose vs Kubernetes?
Route guards and global 401 handling on the frontend?

Short answer: Guards hide screens the user can't use; interceptors handle cross-cutting HTTP concerns. Neither is security; the server is.

How we used it: PrivateRoute / RoleRoute plus an Axios interceptor that attaches the token and logs out on 401.

Follow-ups: Why are client guards not security? · How would refresh-token rotation fit into the interceptor?
Why separate app.js from server.js? What is a service layer?

Short answer: Separating composition from runtime enables testing. A service layer holds business logic so controllers only translate HTTP.

How we used it: Supertest imports app.js; tokenService is the first service. Most logic still sits in controllers, which is the next refactor.

Follow-ups: Controller vs service vs repository? · How does dependency injection help testing?
How do you prevent a race condition like double-booking?

Short answer: Enforce the invariant atomically in the database (unique constraint or transaction), not with a read-then-write in code.

How we used it: A partial unique index on doctor, date and time for scheduled appointments; duplicate key → 409.

Follow-ups: What is a partial index? · When do you need a MongoDB transaction? · Optimistic locking?
What is idempotency, and why does it matter for payments?

Short answer: Repeating an operation has the same effect as doing it once. Networks retry; payments must not double-apply.

How we used it: Verifying an already-paid bill returns success without changes; the bill is found by stored order id.

Follow-ups: Idempotency keys? · Why use webhooks as well as client callbacks? · What is a timing attack?
What is a design system, and how does accessibility fit?

Short answer: Shared tokens and components that make UI consistent by default. Accessibility is built into those components, not added per page.

How we used it: CSS variables, .btn/.surface, PageLayout, skeleton, empty state, toasts; skip link, focus ring, keyboard-operable controls.

Follow-ups: What is WCAG AA contrast? · How do you test with a screen reader? · Tokens vs component library?

5 · Learning Roadmap

Not lessons, just enough to make you curious. Suggested order: Validation → Error middleware → JWT & refresh tokens → Testing → GitHub Actions → Docker → Service layer → React Query → Redis.

API Validation Beginner

What: Declarative rules that reject malformed input before business logic runs.
Why it's cool: One schema can validate, type your code (Zod), and generate API docs.
Here: Stopped the admin-registration exploit and ObjectId 500s.
Industry: Every public API: Stripe, GitHub, Shopify.
Learn next: Zod schemas · schema-to-OpenAPI · validation vs sanitization
Docs: express-validator.github.io · zod.dev · OWASP Input Validation Cheat Sheet · Time: 1 week

Error Middleware Beginner

What: A 4-argument Express middleware that turns errors into responses.
Why it's cool: Deletes hundreds of lines of try/catch boilerplate.
Here: Made the unreachable global handler the single error path.
Industry: Every Express, Nest or Fastify service.
Learn next: Express 5 async errors · RFC 9457 problem details · error monitoring (Sentry)
Docs: expressjs.com/en/guide/error-handling.html · Time: 2-3 days

JWT Authentication Intermediate

What: Signed, self-contained tokens that prove identity without a session store.
Why it's cool: Paste a token into jwt.io and see your own claims, then learn why alg: none was a real exploit.
Here: Pinned algorithm, generic login errors, live user check.
Industry: Auth0, Firebase, AWS Cognito, most SPAs.
Learn next: claims (exp, iat, aud) · HS256 vs RS256 · JWKS · storage trade-offs
Docs: jwt.io/introduction · OWASP JWT Cheat Sheet · Time: 1 week

Refresh Tokens Intermediate

What: Short-lived access tokens plus a long-lived refresh token in an httpOnly cookie.
Why it's cool: Rotation detects stolen tokens; it's how Google keeps you signed in safely.
Here: The next fix: move the token out of localStorage and plug refresh into the interceptor.
Industry: OAuth 2.0 everywhere.
Learn next: rotation and reuse detection · SameSite cookies · CSRF
Docs: auth0.com/docs (refresh token rotation) · OAuth 2.0 RFC 6749 · Time: 1 week

Service Layer Pattern Intermediate

What: Business logic in plain modules; controllers only translate HTTP.
